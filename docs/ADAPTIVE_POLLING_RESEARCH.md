# 自适应轮询研究（状态：**仍开放，未进入生产**）

> 结论先行：目前**没有任何自适应策略达到预先写定的“优于固定轮询”标准**，生产默认仍是 `fixed_interval`。
> 本文记录问题、方法、结果和未解决的问题，供后续继续研究。研究代码与实验数据在 [`research/adaptive_polling/`](../research/adaptive_polling/)（仿真器、策略实现、32 个单元测试、实机竞赛与重放脚本、结果表与图）。

## 1. 要解决的问题

B 要在 A 的压缩包就绪后尽快发现它，但**出包时间不可预知**：A 按“满 N 个文件 / 满字节数 / 最老文件等待超时”成批，图片什么时候来取决于生成器。固定间隔轮询的发现延迟平均约为 T/2、P95 约 0.95T，周期越短查询越多（每次一次 SSH）。

自适应轮询想在“查询次数”和“发现延迟”之间动态取舍：到达密集时查得勤，空闲时查得稀。

约束（来自设计方案 PATCH-01）：
- 策略只决定“何时发起下一次 READY 查询”，不得影响 READY / ACK / 验包 / 删除语义；
- 网络失败不是“没有包”，不得计入到达率估计；
- 只在成功扫描后调用 `observe`，空扫描是有效的“零到达”观测。

## 2. 方法

### 2.1 离线仿真（由子 agent 完成，**我复跑了它的 32 个单元测试，全部通过；实验数字未独立重算**）

- 7 种工作负载：泊松、近似周期、ON/OFF 突发、速率漂移、日周期、长空窗后突发、打包器触发。
- 网络故障轨迹预先生成并在各策略间配对共享；每个 run 96 小时；24,780 次仿真。
- 代价 `J = c·查询次数 + 总发现延迟`，c = 一次查询值多少秒延迟，取 {3,10,30,100,300}。
- 候选：固定间隔（5 档与 18 档）、Gamma–Poisson（设计方案原式与平方根律）、间隔 EWMA + 窄窗口探测、hazard 更新过程（带删失条件化），以及 long_poll 作参考上界。
- 预注册判定 G1–G6：主收益、不伤害、尾延迟、负控制、可靠性、资源。

### 2.2 真实服务器上的实机竞赛（我做的）

11 个策略（5 档固定 + 6 个自适应配置）同时对同一台真实 A 做只读 `list-ready` 轮询，到达节奏：
前 3 分钟每 10 秒 1 个包，中间 4 分钟每 20 秒，最后 3 分钟每 15 秒，共 42 个包。
自适应策略的参数按时间尺度缩放过（原默认值假设“小时级”流量）。

## 3. 结果

### 3.1 仿真（子 agent，c=30，相对 18 档细网格固定周期，正数 = 自适应更好）

| 工作负载 | gp_sqrt | renewal | hazard |
|---|---|---|---|
| 泊松（负控制） | −0.2% | −11.3% | −5.3% |
| 近似周期 | −0.6% | +21.9% | **+45.4%** |
| 打包器 | −1.2% | +15.8% | +16.4% |
| 长空窗后突发 | +12.6% | +17.4% | **+26.3%** |
| ON/OFF | +5.6% | +2.6% | +7.4% |
| 漂移 | +6.7% | −1.1% | +4.1% |
| 日周期 | +4.9% | −2.9% | −0.6% |

判定：四个自适应策略**都没有通过**。hazard 最接近，但在平稳泊松上输 3%–10%（G2），且除近似周期外 P95 变长到 1.2–1.8 倍（G3）。

### 3.2 实机竞赛（42 个真实包，单次运行）

| 目标 | 最优 | 说明 |
|---|---|---|
| 延迟优先（c=3） | `hazard` c=3 | 平均延迟 3.4 s / 59 次查询；最好的固定 5 s 为 4.2 s / 73 次 |
| 均衡（c=10） | `hazard` c=10 | 与固定 15 s 基本打平（J 12.0 对 12.1） |
| 省查询（c=30） | 固定 30 s / 20 s | hazard 反而差约 20% |

在这条真实到达时间线上随机平移轮询起点重放 60 次，排名结构不变，c=10 下前几名差距在噪声范围内。
**局限**：单次实机、到达模式严格分段周期（对 hazard/renewal 最有利，是上限而非常态）、11 个轮询者并发使本机单次扫描变慢（≈3.4 s，各策略相同）。

### 3.3 学习速度（实机）

- hazard：节奏切换后约 3 个包内学会（c=3：前 3 个包 5.6 s → 后 3 个 3.0 s）。
- renewal：学得快，但查询最多（76 次，高于固定 5 s 的 69 次）。
- gp_sqrt（c=10）：反应慢，切到 15 s 节奏时前 3 个包延迟 14.3 s。

## 4. 对设计方案的修正建议

- **设计方案 §8.1 的缩放律需要修正**：`T = poll_factor·3600 / r̂` 让 T 与 1/λ 成正比；仿真显示应与 1/√λ 成正比（`T* = √(7200·c/λ)`）。c=300 时原式比最佳固定周期差 24%–52%。
- **选对固定周期本身就值 2%–9%**，且没有在线学习风险。
- hazard 的收益来自对“当前未结束间隔”的删失条件化（去掉后近似周期场景由 +49% 变为 −38%）。

## 5. 目前采用的实际方案：不预测，让 A 通知

与其预测不可预知的出包时间，不如让 A 在出包时通知 B：

- A 增加只读命令 `wait-ready`（挂起等待，有新的 READY 事件立即返回，否则超时返回无变化）；
- B 在后台线程长挂该请求，返回即触发**一次完整的常规扫描**（游标、事务、对账语义不变）；
- 固定间隔轮询仍保留作安全网。

实测同样的随机到达流量：**发现延迟 `long_poll` 平均 3.0 s（最大 4.2 s），固定 30 s 轮询平均 17.1 s（最大 33 s）**。
代价是 B 到 A 要保持一条长 SSH 连接（约每 55 秒一次重连）。配置见 README。

## 6. 仍然开放的问题

1. 在真实 READY 日志（而非合成轨迹）上做**影子模式回放**，验证 hazard 在真实工作负载上的收益是否站得住。
2. hazard 的门控：仅当已观测间隔 ≥ 20 且变异系数 ≤ 0.5 时启用，并在目标里加入 P95 约束；用**新种子重新预注册**后复核（开发期用过的测试种子不能再用来下结论）。
3. 生产观测对象 `DiscoveryObservation` 目前只有计数，没有 `ready_at` / 快照时刻；`scan_once` 只返回第一次扫描的观测，立即复查那次扫描对策略不可见。接入任何自适应策略前需要补上。`list-ready` 已增加 `server_time` 字段，是第一步。
4. long_poll 作为正式策略的失效处理（连接被中间设备静默断开、半开连接检测）还需要更长时间的稳定性测试。
5. 研究的是“何时查询”。如果更看重发现延迟，更根本的做法是“出站长连接 + 通知 + 低频对账”，目前的 `wake: long_poll` 是其最小实现。
